做后台的时候，我经常碰到一种页面。订单、日志、聊天记录，一拉就是几千上万行。这种页面打开时会先卡一下。卡的原因说起来也不复杂，每一行都做成了 DOM，浏览器得为它们建节点、算布局，图片和套得很深的子树再叠上去，第一次插进文档就能把主线程占住。可你把窗口拉到最大，一屏里也放不下多少行。剩下的那些，人还没滚到，开销已经付过了。

滚动条倒还是需要的。用户要能拖到第 8000 行，总高度就得按完整内容来。所以「内容有多高」和「这一帧文档里有哪些节点」其实是两笔账。我自己写的时候，起先把虚拟滚动和虚拟列表当成一个词，代码也揉在同一个函数里。后来高度对不上、画面自己跳，才把它们拆开。滚动层看滚动位置，决定这一帧准备哪些索引，并把占位撑起来。列表层拿到这些索引，把数据画进有限的节点，再把每条的高度交回去。滚动层没有这张高度表，行高不一的时候窗口就算歪；列表层没有窗口，就不知道该准备几个节点。

## 技术点

* 滚动层：视口、占位、窗口平移
* 列表层：快照、标识、复用池、可变高度
* 两层每帧交接的输入和输出

## 前置知识

后文这几个词我按下面的意思用，不再混。

* 索引

  索引是条目在**当前这份数据**里的位置，从 0 计。滚动层用索引描述窗口。插入、删除、排序都会把索引改掉。

* 标识

  标识是一条数据在列表活着的这段时间里的身份。窗口滑过去，它不该变。头部插入或者重新排过序，同一条数据仍然要给出同一个标识。

* 宿主

  宿主是留在文档里的那个节点，或者包住一条条目的组件实例。数据不是节点。后面说的复用池里放的就是宿主。

* 窗口

  窗口是滚动层算完后交给列表的一段索引，从 `start` 起到 `end` 止，含 `start`，不含 `end`。它经常比肉眼看见的区域再宽一两截，多出来的用来垫即将滚进来的内容。这段区间怎么划，是滚动层的事。

另外三个长度，后面会反复用到。一个限了高度、又写了 `overflow: auto` 的元素，就是滚动容器。`clientHeight` 是视口高度，也就是里边看得到的那一段。`scrollTop` 是内容已经往上卷走多少，视口上沿在内容坐标里的位置就是它。`scrollHeight` 是内容总高度，滚动条能走多远，看的是它和视口的差。视口盖住的区间可以写成 `[scrollTop, scrollTop + clientHeight)`。所谓滚动，就是把这段区间在内容上挪一挪。`scrollTop` 太大时浏览器会钳住，上限大约是总高度减去视口高度。内容比视口还矮的时候，`scrollTop` 就停在 0，虚拟化也没什么可做的。

屏幕高 600 像素、行高 40 像素，视口里大约 15 行。一万行里，这一帧真正用得上的就是这 15 行，再加上贴着视口边缘的几行。

## 滚动层

滚动层只管几何。它不关心第 25 条是哪一笔订单，也不负责把文本写进节点。给定总条数、每一条的高度、当前的 `scrollTop`，它要交出这一帧的窗口，以及窗口起点离内容顶部有多远。高度若和上一帧不一样，它还得决定 `scrollTop` 要不要跟着改，免得用户没滚，画面自己动。

### 行高固定时，窗口就是一次除法

先假定每一行一样高，记成 `itemHeight`。行高后来会变，算法是在这个模型上改，不是另起一套。

```js
function visibleRange(scrollTop, viewportHeight, count, itemHeight) {
  const start = Math.max(0, Math.floor(scrollTop / itemHeight));
  const end = Math.min(count, Math.ceil((scrollTop + viewportHeight) / itemHeight));
  return { start, end };
}
```

拿一组具体的数。`scrollTop = 1000`，行高 40，视口 600，一共一万条。上沿 `floor(1000 / 40) = 25`，第 25 条的顶正好在 1000，贴着视口。下沿 `ceil(1600 / 40) = 40`，可见的是 `[25, 40)`，十五条。第 39 条占 `[1560, 1600)`，下沿和视口下沿对齐。第 40 条的顶在 1600，右开区间不把它算进去。上沿若落在某一条中间，`floor` 给出的是这一条，不是下一条。下沿若正好落在某一条的顶上，`ceil` 让这一条留在窗口外面，零高度的相交不算看见。

第 `i` 条的顶是 `i * itemHeight`。宿主用绝对定位、相对内容的原点来摆的话，写成：

```js
host.style.transform = `translateY(${index * itemHeight}px)`;
```

滚动过程中改的是偏移。`transform` 省下的是「为了挪一行，把周围再布局一遍」。文字自己那一次布局省不掉，行高在样式里还是要写成 `itemHeight`。

可以把它想成一条很长的卷，上面开了一扇窗。这个比方不完全贴切，但窗口的上沿贴在卷的哪里，就是 `scrollTop`。

```
内容坐标
0        1000      1600                         400000
|--------[ 视口 600px ]-------------------------|
          可见 [25, 40)
```

快滚的时候，合成器往往先把已经画好的层移开，脚本要等下一帧才把新索引摆上去。窗口若和视口严丝合缝，边缘会闪出一条空白。所以实际交给列表的窗口，通常比可见区间再宽一点，一般叫过扫描。固定行高时，两侧各扩 `overscan` 条，再钳进 `[0, count)`：

```js
function windowRange(scrollTop, viewportHeight, count, itemHeight, overscan) {
  const start = Math.max(0, Math.floor(scrollTop / itemHeight) - overscan);
  const end = Math.min(
    count,
    Math.ceil((scrollTop + viewportHeight) / itemHeight) + overscan,
  );
  return { start, end };
}
```

`overscan = 2` 时，刚才的 `[25, 40)` 变成 `[23, 42)`。多出来的四条按自己的偏移放在视口外面，总高度不加它们。过扫描垫的是帧和帧之间的一小段，不是一次甩动的全部距离。`scrollTop` 在一帧里跳了 2000 像素，两行盖不住，这一帧仍然得按新位置把整个窗口重算一遍。单元格比较轻、行高又固定，上下各留 3 到 8 条往往就够。单元格里有图、有很重的子树，多留 10 条首屏就能感觉到慢，那就收回去，快滚再露白，再加一两行。行高差得很大时，按条数留会一会儿过多、一会儿不够，改成在高度和上向外扩一段像素更稳。

列表层会把整个窗口都画上，视口外面那几条也走渲染。所以渲染函数被调用，不等于用户看见了。看见没有，还是用视口那段区间来判断。

### 占位把总高度还回去

只把 15 个宿主放进容器，`scrollHeight` 就只剩 15 行那么高。滚动条短得几乎不能拖，`scrollTop` 也到不了 1000，后面的索引永远不会被算出来。

占位元素不表示任何一条的内容，它只占尺寸。固定行高时，把它的高度写成 `count * itemHeight`。一万条、行高 40，就是 400000 像素。`scrollHeight` 回到完整内容的高度，滚动条的比例、拖滚动条能到达的位置，就和每一行都在文档里时一样。行高不固定的时候，占位是全部高度之和，也就是后面要说的前缀和的最后一项。那些高度是列表层按标识交过来的，滚动层负责把它们加总。

摆法我见过两种，几何上是一回事。

一种是一块占位撑满，宿主绝对定位。占位留在正常流里。每个宿主 `position: absolute`，再用 `translateY` 放到该条的顶。宿主离开了正常流，不会把占位再撑高一截，也不会互相推。

另一种是上下两段占位，宿主留在正常流里。上面那段等于窗口起点之前的高度，固定行高时就是 `start * itemHeight`。中间按顺序放窗口里的宿主。下面那段是剩下的高度。三块加起来还是总高度。滚动的时候改这两段的高度，宿主会跟着文档流落到新的位置。

还是用上面那组数，窗口先按可见区间 `[25, 40)` 看。一块占位，高度 400000，第 25 条 `translateY(1000)`，第 39 条 `translateY(1560)`。上下两段的话，上段 `25 * 40 = 1000`，中间 15 行共 600，下段 `(10000 - 40) * 40 = 398400`，加起来仍是 400000。中间第一行的顶被上段推到 1000，和绝对定位的第 25 条是同一个位置。

绝对定位的包含块得是内容的顶，不能是视口的顶，不然 `translateY` 的原点就偏了。上下两段里的宿主不要再设绝对定位，上段就推不动它们，行会叠在一起。还有一件事后面会反复碰到：视口里正在看的内容突然跳，多半是窗口起点之上、当时并没有宿主的那段高度变了。那段不能靠去量一个还不存在的节点，只能靠缓存里的高度。

### 滚动就是窗口在平移

`scrollTop` 从 1000 变到 1040，行高 40，可见区间从 `[25, 40)` 变成 `[26, 41)`。第 25 条离开，第 40 条进来。拖滚动条的时候，`scrollTop` 可以在一帧里跳过几百条。窗口按新的 `scrollTop` 整段重算，不是一条一条挪过去。

滚动层这一帧要公布的，是新的 `start`、`end`，窗口起点在内容坐标里的偏移，以及视口打算钉住的那条数据。钉住谁，用的是标识。标识哪一条对得上哪个索引，列表层去对。滚动层拿到新索引之后，把 `scrollTop` 设到该条的顶，再加上视口上沿在这条内部已经走过的那段距离。

节点个数维持在窗口长度附近。离开窗口的索引这一帧不再需要宿主，新进来的索引需要一个。同一帧里滚了很多下，合成一次计算就行，监听用 `passive: true`，浏览器可以先把已有的层滚走，不必等这段脚本跑完。挂上监听之后要先画一帧，不然 `scrollTop` 还是 0 的时候视口是空的。另外，程序自己为了修正高度去写 `scrollTop`，会再进滚动监听。那一次不是用户在滚，跳过去，不然测量和修正会互相叫醒。

至于哪个宿主继续画哪条数据，滚动层到此为止。池子怎么领、怎么还，是列表层的事。

### 行高不一样，就得用前缀和

行高各不相同时，第 `i` 条的顶不再是索引乘行高，总高度也不再是条数乘行高，从 `scrollTop` 反查索引的那一次除法一起失效。

滚动层维护一张前缀和 `offsets`。`offsets[0] = 0`，`offsets[i]` 是第 `i` 条的顶，`offsets[count]` 是总高度，也就是占位该写成的那个数。第 `i` 条占据 `[offsets[i], offsets[i + 1))`。表里每一格的高度，列表层按标识提供，滚动层按当前索引去读。还没量过的条先填估计高度，估计值也要加进这张表。不加的话占位是短的，那些条根本滚不到，也就永远量不到。

窗口起点改成找最大的 `i`，使得 `offsets[i] <= scrollTop`。高度非负，前缀和才单调，才能二分。

```js
function findStart(offsets, scrollTop) {
  const last = offsets.length - 2;
  let lo = 0;
  let hi = last;
  while (lo < hi) {
    const mid = (lo + hi + 1) >> 1;
    if (offsets[mid] <= scrollTop) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}
```

`offsets = [0, 40, 100, 130]`，一共三条。`scrollTop = 100` 得到 2，第 2 条的顶贴着视口上沿。`scrollTop = 99` 得到 1，第 1 条占 `[40, 100)`，99 还在它里面。`scrollTop = 0` 得到 0。一条和视口相交，要同时满足两件事：它的顶在视口下沿之前，它的底在视口上沿之后。从起点往后收到第一个不满足的索引，那个索引就是 `end`。

把视口对准第 `index` 条，就是让 `scrollTop` 等于 `offsets[index]`，再按浏览器的上限钳一下。窗口外面没有节点。要对准它，得先按这个偏移把 `scrollTop` 设过去，窗口盖住那个索引，节点才会出现。不能等节点出现了再叫它自己滚进视口，调用发生的时候节点还不在。高度若还是估计值，这一下对准的只是估计位置。该条进入窗口、列表层量出新高度之后，`offsets[index]` 可能变了，用户这会儿又没有在滚，就再设一次。用户正在滚，就不要做这第二下，滚轮和修正会抢 `scrollTop`。

测量带来的差记成 `delta`。前缀和从这条的下一条起到末尾都加上 `delta`，占位跟着变。`scrollTop` 改不改，看修正之前这条的底边在不在视口上沿之上。

```js
function applyDelta(offsets, index, delta) {
  for (let k = index + 1; k < offsets.length; k++) offsets[k] += delta;
}

const oldBottom = offsets[index] + heights[index];
const delta = measured - heights[index];
heights[index] = measured;
applyDelta(offsets, index, delta);
if (oldBottom <= scrollTop) viewport.scrollTop = scrollTop + delta;
```

底边已经在上沿之上，多出来的厚度都在视口外面，`scrollTop` 加上 `delta`，上沿才还对着原来的内容。底边还在视口里面，多出来的像素长在看得见的地方，`scrollTop` 不动，只是总高度变了。有一种容易弄反的情况：一条跨在上沿上，顶在上沿之上，底在上沿之下。多出来的像素通常长在这条的下部，也就是视口内部，不能因为它的顶在上面就把整个 `delta` 加进去。`delta` 是负数、这条变矮时，判断一样，结果小于 0 要钳住。同一帧里好几条一起变，要用更新前的偏移判断哪些底边在上沿之上，把这些 `delta` 加总，再改一次 `scrollTop`。边改前缀和边判断，后面的条会用到已经变过的坐标。

用四条走一遍，估计高度都是 40，所以 `offsets = [0, 40, 80, 120, 160]`，视口高度 100，`scrollTop = 80`，起点是 2。第 2 条量得 70，修正前底边是 120，大于 80，底边在视口里，`scrollTop` 不动。第 2 条的顶仍是 80，第 3 条的顶变成 150，总高度变成 190。用户看见的是这一条在视口里变高，下面的内容往下让。换第 0 条，量得 60。修正前底边是 40，`40 <= 80`，整条都在上沿之上，`scrollTop` 变成 100，从第 1 条起每条的顶都加 20。原来贴着内容坐标 80 的那条线，现在在 100，视口上沿跟着过去。

上下两段占位里，窗口上方任何一条变高，都体现在上面那段变高，中间的宿主被往下推。要保住视口里的内容，同样得把多出来的高度补进 `scrollTop`。

浏览器自己的滚动锚定只看文档里已经有的节点。窗口外的条不在文档里，它们变高、被插到前面，锚定看不见。所以这件事得自己做，做在 `scrollTop` 和占位上。

人没滚、视口上方的高度却变了，用的也是这条规则。聊天记录往上补旧消息就是这样。头部插入一段总高为 `h` 的内容，已有各条的顶都增加了 `h`。`scrollTop` 不加同样的量，上沿会改而对着更靠前的一条，画面就被拽到顶上。更新前记下上沿所在那条的标识，以及 `scrollTop` 减去该条的顶。列表层在新快照里把标识换回新索引，滚动层再把 `scrollTop` 设成新的顶，加上那段距离。只记索引的话，插入之后钉住的就是另一条。插入若发生在视口下沿之后，看得见的内容不动，只增加总高度。

## 列表层

列表层不自己划窗口。滚动层把区间、起点偏移、锚点标识给它，它保证窗口里每个索引画的是该索引上的那条数据，离开窗口的宿主不把上一条的状态带走，变过的高度下一帧还认得出是谁。

### 列表认的是一份能按下标读的快照

滚动层只会说「给我第 i 条」。数据源得能按索引取值，并回答现在一共有多少条。在这份快照被换掉之前，同一个索引每次取出来的条目和标识得是稳定的。随机数、读取的时刻、还没回来的请求，都不能直接当标识。

```typescript
type Source<T> = {
  count: number;
  item: (index: number) => T;
  key: (index: number) => string;
};
```

过滤、排序、在头部插入，都是换一份快照，不是在旧数组上把 `count` 改一改。同一帧里前半段用旧数组、后半段用新数组，索引会指到别的条目上。滚动层手里可能还拿着按旧快照算好的窗口。列表层改用新快照时，得让滚动层按新的条数、新的标识、新的高度再要一次窗口。锚点那个标识在新视图里已经没有了，就改钉到还在的邻近条目，或者回到起点，并把窗口收进新的条数里面。

来源我常见的有三种，列表认的契约是一样的，都是按索引取值。

内存里的数组最直接，条数就是长度。窗口模型靠这种随机访问。只能往后走的游标，得先变成可以按下标读的结构，才能当数据源。

搜索、筛选、排序得到的是另一份数组，我把它叫视图。源数据里的第 10 条，在视图里可能变成第 0 条，也可能被去掉。勾选若记在业务标识上，视图换了还能对上。记在视图的索引上，下一次筛选就会贴到别的条目。

总条数已知、按页去填的那种，还没加载的下标也得占位置。该位置放一条占位条目，高度用估计值。不占的话，窗口会把后面的真实数据提前画出来。占位条目同样要有稳定标识。服务端已经给出 id，就用这个 id。只有页结构的时候，用页号加页内序号，真实数据到达之后继续沿用。标识一旦换成另一个，高度缓存和宿主都会把「加载完了」看成「换了一条数据」。

总条数暂时还不知道的时候，列表可以随着已经加载的条数变长。这时交得出当前这段的占位，交不出最终的滚动条比例，「已经滚到末尾」也没有一个最终长度。窗口靠近已加载范围的边缘，再去请求下一页，请求回来就替换快照。请求是在填数据，不是在画。

### 索引是地址，标识是身份

在头部插入一条，原来排在 0 的那条变成 1，标识不变。高度若按索引存，整张表就错一位。按标识存，还能找到。锚点若只记了索引，插入之后钉住的就是另一条。列表层交出的是标识和当前索引的对应，滚动层用这个标识去新快照里找索引。

标识得满足三条。当前这份快照里唯一。同一条逻辑数据换了快照仍然不变。不要掺进会变的渲染结果，比如把标题和当前高度拼成一个字符串，一测量标识就变了。用索引当标识，只在这份快照的前缀不会插入、删除、重排时才成立。头部插入、排序、过滤、删掉中间某一条，原来的索引都会指向另一条。表现通常是两种。协调器把节点当成全新的，焦点和输入丢了。或者节点留着，状态贴到了新索引上。后一种更不容易注意到。没有业务 id 的时候，在数据进入列表之前补一个稳定的，不要等渲染时再造一个随机数，也不要悄悄退回用索引。

位置是布局算出来的偏移。不能靠「离顶部多少像素」把一条数据找回来，也不能靠标识直接推出它这一帧的偏移。高度缓存用标识做键，交给滚动层的时候再按当前快照换成索引。

### 渲染写的是宿主，宿主可能是旧的

渲染函数至少要拿到条目、它在快照里的索引、这个宿主上一帧绑的标识。

```typescript
type Paint<T> = (
  el: HTMLElement,
  item: T,
  index: number,
  previousKey: string | null,
) => void;
```

索引用来写和位置有关的信息。`aria-posinset` 可以用索引加 1，`aria-setsize` 用快照的条数。索引不用来认人。同一条数据滑出窗口再回来，中间若插入过，索引可能已经变了，身份只看标识。

宿主可能画过别的数据。只在新建节点的时候赋值，复用之后屏幕上会留下上一条的文本、属性和监听。标识没变的宿主，只更新能从数据推出来的那部分。数据里没有的字段不要重写。每一帧都用空的草稿去盖输入框，即便按标识复用把节点留住了，打到一半的字也会被写掉。

跟条目走的状态放进数据，或者放进以标识为键的表。勾选、展开、已经决定要留的草稿，都是这种。放在节点的非受控字段上，宿主一换绑就跟到下一条。还没提交、也不打算进数据的临时状态，只有标识不变、这段时间既不复位也不覆盖的时候，才能留在节点上。条目离开窗口，这种状态要么已经抽到那张表里，要么就丢掉。焦点若还在即将归还的宿主里，先给它一个去处，不然它会掉到文档根上。

### 池子里放的是宿主

池是一组已经创建好的宿主。这一帧窗口有多长，池就准备多少。窗口变长再补，变短就把多余的闲置，不要马上销毁。窗口长度会随视口尺寸和条目高度变，反复创建会把省下来的成本还回去。

池的容量跟着窗口走，不跟着数据条数走。一万条数据、窗口长度 20，池里就是大约 20 个宿主。数据再翻一倍，池的规模不变。第一帧按估计高度准备的宿主，可能不够。实测更矮的时候，同一个视口装得下更多条，滚动层下一帧会给出更长的区间，列表层得能补宿主。池比窗口还小就继续领，会把同一个宿主画两次，或者直接拿不到节点。吸顶的那一条若滑出窗口还要留在视口里，就不要用这只普通池里的宿主，单独留一个节点，复用的时候也不要拿它去画别的数据。

按槽位复用，是第 i 个宿主永远画窗口起点之后的第 i 条。窗口往前移一格，每个看得见的槽位都换数据。这种做法适合没有本地状态的条目，纯文本、图标、从数据里读出来的勾选。起点一变，写在节点上的状态就会串到新的索引。当前快照里不存在的索引，不要沿用上一帧的画面，超出条数的槽位藏起来。

```typescript
function renderBySlot<T>(
  items: readonly T[],
  start: number,
  slots: HTMLElement[],
  paint: (el: HTMLElement, item: T, index: number) => void,
) {
  for (let i = 0; i < slots.length; i++) {
    const index = start + i;
    const el = slots[i];
    if (index >= items.length) {
      el.hidden = true;
      continue;
    }
    el.hidden = false;
    paint(el, items[index], index);
  }
}
```

按标识复用，宿主记住自己现在的标识。标识还在新窗口里，就继续用这个宿主。标识离开了，把宿主还回去。新进来的标识从空着的宿主里领。窗口只移动一格的时候，只会换绑离开的那一个。焦点、正在放的媒体、没有写进数据的选区，才留得下来。

```typescript
type Host = { key: string | null; el: HTMLElement };

function takeHost(pool: Host[], key: string): Host {
  const matched = pool.find((host) => host.key === key);
  if (matched) return matched;
  const blank = pool.find((host) => host.key === null);
  if (!blank) throw new Error('池比窗口小');
  blank.key = key;
  return blank;
}
```

快照里的标识必须唯一。两个索引共用一个标识，会先后写进同一个节点。示意里的 `takeHost` 在标识已经绑定时会把原来的宿主再交出去，第二个索引再来领的时候应当直接拒绝。在组件框架里，若这一帧只把窗口内的条目交给协调器，并且每条都带着稳定标识，协调器做的就是按标识复用，不必再手写一套节点池。手写池用在直接操作节点、或者得自己卡住实例数量的时候。两种做法用的是同一套身份，消费的也是同一个窗口。

宿主和一条数据解开的时候，换绑之前先清掉绑在那条数据上的东西。文本，以及只对那条数据有意义的属性。为那条数据注册的监听。非受控输入的值和选区。媒体进度、临时的图片地址。写在节点上的尺寸。高度的正式记录在标识的缓存里，不在节点上。可以留下的是跟具体条目无关的结构，宿主元素、子节点的骨架、通用的样式。骨架留下来是为了少创建节点，骨架上的内容不能留。先写新数据、再指望它把旧字段盖住，漏掉的字段会串。标识没变的宿主不要复位，不然列表稍一滚动，输入框里的字就被清掉。

### 高度记在标识上，比宿主活得久

每条高度都一样的时候，滚动层用除法就行，列表层不必测量。高度随内容变，偏移就是前面各条高度之和。这张表由列表层按当前快照提供，求和和滚动位置属于滚动层。

条目还没进过窗口，就没有实测，此时用估计高度，窗口才算得出来。估计值要标明来源。它参加这一帧的计算，不表示已经量过、以后不用再量。条目进入窗口、布局完成之后，用实测盖掉估计。

```typescript
type SizeRecord = {
  height: number;
  source: 'estimate' | 'measured';
};

function readHeight(record: SizeRecord | undefined, estimate: number): SizeRecord {
  return record ?? { height: estimate, source: 'estimate' };
}
```

测量读宿主的边框盒。写回缓存时，键是数据的标识，不是宿主，也不只是索引。同一个宿主下一帧可能已经换了数据。尺寸只留在节点上，换绑之后量到的是新数据，旧数据的高度却丢了。还没进入窗口的条目，高度只活在这份缓存里。条目滑出窗口，宿主可以归还，记录留下。在它再进来之前，滚动层还要用这条高度去算占位。按索引保存、并在复用时覆盖，会把别人的高度写进已经滑出去的那一格。

一帧之内先把窗口里的内容写完，再集中读高度，最后一次把变化交出去。读一条、改一条样式、再读下一条，布局的成本会跟着窗口长度涨。也可以等布局完成，用 `ResizeObserver` 接收尺寸。回调里仍然按标识写入。不要在回调里同步改样式再立刻读布局，那会把一帧里的测量放大成每个条目一次来回。

图片还没解码、手风琴还没展开，这类还会变高的条目，要把标识标回待测，下次它在窗口里再量一次。标成实测之后又永不失效，第一次量错的高度会一直参与它上方的占位。视口变宽、字号变了、容器宽度变了，也是把记录标成待测，不必把池拆掉。

实测和缓存里的旧值不同，才产生一条变化。

```typescript
type SizeChange = {
  key: string;
  index: number;
  prev: number;
  next: number;
};
```

比较之前，先在这一帧的快照里把锚点标识换成索引。变化的索引小于锚点，这条在锚点上方，同样的内容离文档顶部更远了，要让画面不动，滚动偏移得加上两次高度的差。变化的就是锚点，并且锚在该条的顶边，顶边不动，条目向下长，滚动偏移不变。变化的索引大于锚点，影响的是锚点以下的内容，滚动偏移不变，总占位变长。列表层把变化交出去，掌握 `scrollTop` 的那一层去加。只改缓存、不交变化，上方一张图片加载完，正在读的那一行会被顶下去。只改滚动偏移、不改缓存，下一次按高度表求和又用到旧值，跳动会在后面的帧回来。

用户若已经滚进一条很高的条目内部，锚点就不只是顶边，还包括顶边之下的一段距离。只有这段距离之上的变化才调整偏移。水平列表记的是宽度，规则相同。网格仍然按索引取数据。一个可视行里有多列的时候，先约定索引按行还是按单元格，高度表和窗口必须用同一种约定。

从 48 量到 48，不交非零的变化，但要把来源从估计改成实测。同一条滑出去再进来，图片解码使它变成 80，而它又在锚点上方，就要更新该标识的缓存，并把滚动偏移加上 32。

## 两层之间交什么

每一帧我按下面的顺序走。两边都不要把对方的账再算一遍。

滚动层用上一帧已经提交的高度表、当前的 `scrollTop` 和视口高度，算出窗口，并给出锚点标识在这一帧快照里的索引。列表层只在这个窗口里领宿主、写数据、测量，把高度变化交回来。滚动层再按变化落在锚点的哪一侧，改前缀和、占位，以及必要的 `scrollTop`。

列表层拿到的是三样。当前快照上的窗口，从 `start` 到 `end`。窗口起点在内容坐标里的偏移。锚点的标识，它在这一帧里能换成索引。

列表层交回的也是三样。每个索引对应的标识。该标识的高度，并标明是估计还是实测。高度相对上一帧的变化量，以及这条数据在锚点的哪一侧。

```typescript
type Range = { start: number; end: number };
```

节点最后摆在哪个偏移上，滚动层用这些高度去算。列表层不改 `scrollTop`。窗口内部可以按普通文档流往下排，某一条变高，窗口自己会被撑开。会把视口里正在看的内容顶走的，是窗口起点之上、当前没有宿主的那段高度。那段的变化必须出现在交回来的 `SizeChange` 里。

用六条数据把这一帧走完。标识就是 a 到 f。

| 索引 | 标识 | 高度 | 来源 |
|------|------|------|------|
| 0 | a | 40 | 实测 |
| 1 | b | 80 | 实测 |
| 2 | c | 40 | 估计 |
| 3 | d | 120 | 实测 |
| 4 | e | 40 | 实测 |
| 5 | f | 40 | 估计 |

滚动层第一次给出的窗口是索引 1 到 5，也就是 b、c、d、e。锚点是 d，锚在 d 的顶边。池里准备 4 个宿主，这一帧之前都是空的，四个标识各领一个，没有宿主要复位。c 进入窗口后量到 72，不再是估计的 40。c 的索引 2 小于锚点索引 3，列表层交出变化：标识 c，旧高度 40，新高度 72。滚动层把偏移加上 32，视口里 d 的顶边才不会被顶走。缓存里 c 改成 72，来源改成实测。b、d、e 的实测没有变化，不交非零差值。

下一帧滚动层把窗口改成索引 2 到 6，也就是 c、d、e、f。列表层不算「为什么变成这四个」，只处理宿主。b 不在新窗口里，它的宿主归还，清掉 b 的文本和监听，标识置空。c、d、e 的标识还在，宿主不动，也不复位，渲染只更新能从数据推出来的字段。f 领走刚才空出来的宿主，写入 f 的内容。f 量出来仍是 40，和估计相同，不交非零变化，来源改成实测。池的长度还是 4。后面再追加一百条，只要窗口仍是 4 个索引，宿主就不增加。

如果这一帧不是窗口平移，而是在索引 0 插入一条新数据，a 到 f 的索引全部加一，标识不变。c 的高度仍然记在 c 上，不会跟着旧的索引 2 走。锚点仍是 d，滚动层要用 d 去新快照里找它现在的索引，而不是继续钉着插入前的 3。新插入的那段在 d 的上方，它的高度要进滚动偏移，眼前这条才会留在原地。

写的时候，这几处我自己也错过。用索引当标识，同时又允许头部插入或排序，高度、勾选和输入会整表挪位。高度按索引缓存，窗口一滑，滑出去的位置就被写成新条目的高度，上方的占位跟着错。换绑的时候不复位，按槽位复用尤其明显，非受控输入、图片地址、表示展开的类名留在槽位上，数据已经是新的，界面还是旧的。标识没变，渲染却把非受控字段盖掉，节点留住了，值仍然每帧被写回。估计值当成最终值，或者图片解码之后没有把标识标回待测，重叠、空隙、滚动条长度不对，都从这里来。上方变高却不交变化量，缓存已经是新高度，滚动偏移还是旧的，视口被顶走。同一帧混用两份快照，滚动层按筛选前的索引要窗口，列表层已经换成筛选后的数组，应当整份替换，用锚点标识重新取窗口。池按数据条数创建，文档里就仍然有完整的一份节点。把渲染当成曝光，窗口里多准备的那几条也会被算成「看见了」。

`content-visibility: auto` 可以让浏览器跳过屏外内容的布局和绘制，`contain-intrinsic-size` 还能给还没布局的内容一个占位尺寸。元素还在文档里，数据变长时节点数仍然跟着条数走。那是浏览器在跳过渲染，不是按窗口去领宿主。分页改变的是数据一次来多少。一页之内如果仍为每一行创建节点，长页一样贵。分页可以拿来当加载策略，绘制仍然只覆盖窗口。

## 总结

本文把长列表拆成滚动层和列表层来写。我们提及了：

* 滚动层如何用视口和 `scrollTop` 划出窗口，并用占位把总高度交回去
* 行高不等时，前缀和、滚动定位，以及底边在视口上沿之上才改 `scrollTop`
* 列表层的快照、标识、复用池，以及高度记在标识上、宿主归还后记录还在
* 两层每帧交接的输入和输出，以及锚点上方、自身、下方三种变化分别怎么处理

现在，你应该能把「窗口算到哪」和「节点上画的是谁」分开看了。高度只要有一边还拿着旧值，下一帧跳动就会回来。
